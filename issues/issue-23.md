# Issue 23: duplicate creation message and physician list

## Findings

This is a source-code analysis; the reported incident and Figure 3 were not reproduced or available for inspection in this session. No application code was changed.

- A single successful submission causes **two visible status messages**. [`CreateForm`](../web/src/features/identity/PhysiciansPanel.tsx#L32) sets `created` and renders “Physician created.” inside the form; its `onCreated` callback also sets the same parent `notice`, rendered above the form ([lines 553–565](../web/src/features/identity/PhysiciansPanel.tsx#L553)). Both are `role="status"` elements, not evidence of two HTTP requests or a toast library. A double submission is not needed to explain the duplicate. The current button already uses `disabled={busy}` and changes its label during the POST ([line 117](../web/src/features/identity/PhysiciansPanel.tsx#L117)); the handler has no explicit re-entry guard. Each call generates a fresh idempotency key ([api.ts](../web/src/features/identity/api.ts#L229)), so backend idempotency does not deduplicate separate submissions.
- [`list_physicians`](../backend/src/x_insight/identity/service.py#L339) counts and selects **all** user rows, without a role predicate, before ordering and pagination. The route returns those rows directly as safe users ([router.py](../backend/src/x_insight/identity/router.py#L484)). This includes the administrator and makes `total` include non-physicians. S04 explicitly recorded that behavior as an unresolved follow-up ([S04](../project-documents/dev/progress/s04.md)).
- A successful create already calls `reload()` ([PhysiciansPanel.tsx](../web/src/features/identity/PhysiciansPanel.tsx#L561)), and the identity router uses `CommittedRoute`, which commits before sending the response ([db.py](../backend/src/x_insight/db.py#L112)). Thus the source does not establish a missing refresh or a post-response commit race as the cause of Figure 3. However, the list fetches only the first 100 rows in username order ([api.ts](../web/src/features/identity/api.ts#L221)); a newly created name outside that page will not be shown even after a successful refresh. Existing theme tests acknowledge this cap ([themes.spec.ts](../e2e/themes.spec.ts#L254)). Also, concurrent `reload` calls have no ordering guard, so an older response can overwrite a newer one. These are demonstrable limitations, not a proven explanation of the particular screenshot.
- The other service caller, CSV export, walks all bounded pages and filters the role itself ([reporting.py](../backend/src/x_insight/cases/reporting.py#L170)); query-level filtering changes its input and total but should retain its physician-only output. Existing browser tests scope their success assertion to the form and therefore miss the duplicate ([identity.spec.ts](../e2e/identity.spec.ts#L239)).

## Minimal implementation plan

1. In `PhysiciansPanel.tsx`, keep the existing form-level success status and remove only the creation callback's duplicate parent notice. Keep the existing `busy`-disabled submit button and its `finally` reset; add a synchronous in-flight guard to the submit handler so rapid or programmatic re-entry cannot start another POST before React renders the disabled state. Release it on both success and failure. Preserve validation and session-expiry behavior.
2. In `identity/service.py`, add `role == PHYSICIAN_ROLE` to **both** the count and row queries, before pagination. Keep inactive physicians, ordering, bounds, authorization and safe response shape unchanged. Update the now-false explanation in `cases/reporting.py`; its redundant role check can stay to avoid unnecessary behavior changes. Check all callers and existing assertions against the corrected physician-only total.
3. Keep the existing post-create reload and use the returned created physician from `createPhysician`. Ensure a successful reload displays that account even when it falls outside the first 100: include the returned row once by ID if the fetched page omits it, preserving the server's total and indicating the bounded page where applicable. Show it promptly while the refresh is pending when there are existing rows. Prevent an older overlapping reload from replacing a newer response (including its error state); do not invent a second refresh mechanism. On a refresh failure, retain the existing visible error and Retry path rather than presenting a stale list as current. Preserve sorting as far as possible and avoid duplicating the row when it is already in the response. The special inclusion is for the just-created row, not a replacement for full pagination.
4. Extend the focused existing tests: backend HTTP coverage should verify an admin plus active and inactive physicians, physician-only `items` and `total`, and limit/offset after filtering, including an empty physician list. Keep the CSV export regression and verify its output still excludes admin. Browser coverage should assert exactly one success status across the whole page, one POST under an intentionally delayed response and repeated submission, disabled/re-enabled button including failure, a fresh GET after success, and the new row without a page reload. Exercise a new row beyond the first 100, delayed out-of-order GET responses, no duplicate row, and refresh failure/Retry. Retain the existing form-level status checks and theme contrast tests.
5. Run the focused physician HTTP and CSV export tests and identity browser coverage with the configured backend, plus the web build. Record actual results and any unavailable environment in the progress handoff; do not claim the original incident is verified without reproducing it.
