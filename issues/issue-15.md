# Issue 15 — Provider capability mode and environment override

Date: 2026-11-01  
Status: implementation present; UI clarification and focused checks complete; end-to-end acceptance and independent review remain open

## Requested behavior

An administrator can save `schema` or `json`, see the last test's detected mode, and have new batches use the saved mode without restarting the worker, subject to a valid override. Later jobs in an already pinned batch retain that batch's revision. A deliberate `X_INSIGHT_PROVIDER_CAPABILITY` override still wins, is logged, and is visible in the UI. A local environment override is not required for normal operation.

## Diagnosis

**The reported env-only root cause was real in an earlier revision, but is no longer an accurate description of this checkout.** The B05 reproduction documented the missing settings field, env-only worker and generic probe in [BUGFIX_LOG.md](../docs/BUGFIX_LOG.md#b05-capability-mode-reproduction-2026-10-31). Current commit `84d2d7d` already contains the corresponding implementation. The historical statement that B05 was uncommitted in the earlier handoff predates the [commit handoff](../project-documents/dev/progress/s43.md#follow-up-2026-11-01--commit-current-development-changes).

A valid, nonempty `X_INSIGHT_PROVIDER_CAPABILITY` supplied to a worker overrides the saved selection. An earlier analysis reported a local override, but this follow-up did not read or modify `.env` or inspect any running process, so its current state and effect are unverified. Changing a file does not mutate an already-running process's environment: an operator changing its environment must restart that process once. Do not expose or modify the local environment file without the operator's approval.

With no saved revision it does not claim an effective mode; override status on saved settings reflects the API process, not necessarily the worker.

## Minimal implementation plan and complete change boundary

**Do not rebuild an already-implemented feature.** First reproduce against the actual deployment with a fake provider and check which environment each process received. If the valid local override is the cause, the smallest operational fix is for the operator to remove or blank that override in their own environment and restart the affected process once. Do not delete the variable from deployment support: it remains an explicitly requested override.

1. **Verify existing behavior first.** With no override in API or worker, save `schema` and queue a batch, then save `json` and queue a new batch without restarting the worker. Capture the outgoing response format (`json_schema`, then `json_object`) using the existing fake provider. Check that an earlier queued job still uses its pinned revision. Verify a valid override wins, is logged, and appears on the saved Provider page; ensure API and worker environments agree. Check that the last detected result survives reload and that testing does not silently change the saved selection.
2. **Only if verification exposes a failure**, fix the narrowest existing component responsible for that failure. Permitted areas, conditional on evidence: `backend/src/x_insight/reasoning/provider_config.py` for saved/detected/override resolution and API reporting; `worker.py` or `queue.py` for per-job pinned resolution; `provider.py` for a proven probe error; `web/src/features/admin/provider-settings/ProviderSettingsPage.tsx` and `api.ts` for a proven display or form error. Maintain current validation, version fencing, encrypted credentials and pinned-job semantics. No new abstraction or dependency.
3. **If a text clarification is needed to make the existing workflow understandable**, limit it to the existing Provider page: call the value “Effective mode” and clarify that Test uses saved settings and detection does not select a mode. Do not redesign the page or change probe semantics. Showing an override before any settings exist requires a real API-backed status, not a fabricated frontend value; make that change only if the unsaved state is demonstrated to be required by acceptance.
4. **Tests only as needed:** reuse [the fake-provider worker test](../backend/tests/worker/test_saved_provider.py#L145), [capability tests](../backend/tests/provider/test_capability_mode.py), and [stubbed UI test](../e2e/provider-capability-mode.spec.ts). Extend the smallest relevant test for any demonstrated gap; a stubbed browser test alone cannot prove worker behavior. Exercise invalid/absent override and detection failure if the corresponding path is changed. Preserve existing migration and restore tests.
5. **Documentation only if configuration guidance is found inaccurate:** amend the existing installation guidance narrowly; do not edit or commit a user's local `.env`. Record actual results and any blocker in this issue and the S43 progress handoff/index.

**Outside scope:** new migrations or hand edits to schema; replacing 0027/0028; new provider configuration storage, automatic selection of the detected value, changing defaults or old queued-job pins, changing probe success criteria without a reproduced defect, weakening destination or credential safeguards, unrelated provider/clinical code, broad refactors, dependency additions, and unrelated test repairs. If a proven failure requires a file outside the boundary above, document the dependency before expanding it.

## Acceptance and verification limits

- With no valid worker override, a new batch started after a save can use the saved revision without worker restart. Jobs in an existing pinned batch retain that revision, including jobs queued later; reused batches need not pick up the newer revision.
- A valid worker override takes precedence and is logged; the UI accurately says an override is active **when the API and worker receive the same override**. A changed process environment takes effect after that process is restarted.
- Last-test detection is displayed separately from manual selection; unknown and mismatched results are not presented as verified compatibility. The local `.env` override is optional, not silently required.
- Historical B05 evidence reports a fake-provider worker test, mocked Chromium/Firefox checks and 66 focused backend checks passing ([S43](../project-documents/dev/progress/s43.md#follow-up-2026-11-01--b05-detection-and-worker-acceptance)). The browser test is mocked, and full backend/browser gates and review were not established green. These are historical results, not fresh test runs.
- Fresh follow-up: the focused mocked Playwright suite passed **4 tests** across Chromium and Firefox; root and web TypeScript checks passed; selected DB-free backend tests passed **8 tests**. The browser test checks unsaved edits versus the saved selection, including Test before Save, and the no-saved-mode display. Mocked responses do not prove live worker or provider behavior.
- No `.env` was read or modified in this follow-up, and no live process override was checked. Full deployment, live-provider and continuous-worker acceptance are not established. At the earlier checkpoint the destructive DB test had not been run. Subsequently, the fake-provider worker test passed **1 test in 32.83 seconds** in the backend virtual environment on an isolated PostgreSQL 16 cluster with TCP disabled, which was cleaned up. Two system-Python attempts failed because dependencies were absent. This is not a deployed continuously running worker or a live-provider test. A separate probe review reproduced numeric `1` and `1.0` being accepted as true; the fix requires actual boolean `True`, with parametrized schema and JSON-fallback tests. **11 relevant DB-free tests and Ruff passed**. The 11 DB-free tests were independently rerun and passed. Missing an explicit type alongside `const` was not established as a defect and was unchanged. Final review identified preexisting limitations outside the proven-fix boundary: generation retries a classified HTTP 400 `response_format` rejection without the selected response format, while detection classifies HTTP 422 as a model error rather than probing JSON fallback. Independent frontend review found no actionable findings; no overall review pass or complete acceptance is claimed.
