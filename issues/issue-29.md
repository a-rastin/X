# Issue 29: Favicon and anonymous session probe

Status: implemented and locally verified, 2026-11-03. See the [verification handoff](../project-documents/dev/progress/s03.md#follow-up-2026-11-03--issue-29-verification); deployed acceptance remains unverified.

## Root cause

- `web/index.html` has no icon link, and the frontend has no favicon asset. Browsers may request `/favicon.ico` by convention; when the server does not provide an icon, that request can fail. In production `deploy/Caddyfile` falls back to `index.html` for missing static paths, so verify the actual response is an icon rather than relying on its status alone. The exact reported 404 has not been reproduced in this analysis.
- `web/src/features/identity/auth.tsx` unconditionally calls `refresh()` on mount. `refresh()` calls `me()` in `web/src/features/identity/api.ts`, which fetches `/api/v1/me`. In `backend/src/x_insight/identity/router.py`, a missing or invalid session returns 401. The frontend already catches that `ApiError`, clears session state and shows the login screen; the browser may still log the failed HTTP request. React StrictMode in `web/src/main.tsx` can invoke the mount effect twice in development.
- The session cookie is HttpOnly, so JavaScript cannot reliably check its presence. `xi_csrf_token` in localStorage is not a session authority: storage can be unavailable or cleared while the shared cookie is valid. `/me` deliberately restores the CSRF token for that cookie, including across tabs and upgrades. See the CSRF handoff in `project-documents/dev/progress/s42.md` (2026-10-18). Skipping startup based on localStorage would regress this behavior. Catching 401 alone does not prevent a browser-generated console/network error.

## Minimal implementation: complete change scope

1. Add a small valid favicon at `web/public/favicon.ico` and link it in `web/index.html` with `<link rel="icon" href="/favicon.ico">`. Vite copies public assets to the build root, which Caddy serves. Verify both the URL and bytes/content type, including the built site; do not mistake the SPA HTML fallback for an icon. No new package is needed.
2. Add an **opt-in** anonymous-probe mode to the existing `/me` route, for example `?optional=true`. With that flag, return `200` and a documented minimal body such as `{"user": null}` for missing, invalid, revoked, or inactive sessions; use `Cache-Control: private, no-store`. For a valid session return the existing authenticated payload and cache header unchanged. Without the flag preserve the existing 401 error contract, including for other clients and protected routes. Use the existing server-side session validation; do not infer authentication from the query flag or weaken CSRF, authorization, or cookie settings.
3. In `web/src/features/identity/api.ts`, have `me()` request the opt-in mode and type its result as the authenticated payload or the anonymous body. Call `setCsrfToken` only for the authenticated payload. In `auth.tsx`, handle the anonymous body using the existing 401 cleanup path: clear token, user and warning state and set status anonymous. Keep the existing 401 fallback for compatibility and preserve propagation of other failures. Both startup and the existing password-change `refresh()` caller use this path; retain successful session and warning ingestion. No client-side session marker or new endpoint is needed.
4. Extend the existing identity backend tests to check opt-in anonymous responses for no cookie and an invalid/revoked session, authenticated response and no-store behavior, and unchanged default 401 and protected-route behavior. Add focused browser coverage in the existing identity suite: a clean context records console errors and network responses through initial load, confirms sign-in screen, verifies an actual icon response and no favicon 404 or `/me` 401; then sign in and reload and verify the authenticated screen and a CSRF-protected mutation. Also clear localStorage while retaining the valid cookie and reload, verifying session and CSRF recovery. Retain the existing cross-tab replacement test. Exercise the development and built/preview static paths, and relevant Chromium/Firefox runs where available. Run the focused identity tests and web build; record any environment or browser gaps.
5. Append implementation and verification results to `project-documents/dev/progress/s03.md` and add a short link to its progress index.

## Boundaries and acceptance

Only the favicon asset/link, opt-in identity response and its consumer, focused tests, and required progress documentation need change. Do not change the default `/me` API response, login/logout/password semantics, cookie security, CSRF validation, cross-tab storage behavior, unrelated logging, app design, deployment configuration, or dependencies. Existing mocked `/me` routes and URL-specific tests should be checked and updated only if the query string affects them.

A clean page load must produce no favicon 404 or `/me` 401 in the browser console, with a real icon served. A valid signed-in reload must restore identity, warning state and a working CSRF token, including with cleared localStorage. A stale session should quietly become anonymous in opt-in mode; other errors must not be mislabeled as an authenticated session. Verify these outcomes before claiming acceptance.
