# Issue 21 — Patient names reject spaces and show awkward errors

## Finding and root cause

The current registration contract deliberately requires letters only. The client [`isValidPersonName`](../web/src/features/patients/validation.ts#L40) NFC-normalizes each name and checks it against `^[\p{L}]+$`; a space, hyphen or apostrophe makes the form invalid and disables Register before a request is sent. Its message concatenates the field label with `Must be...`, producing “Family name Must be...”. The registration [hint](../web/src/features/patients/RegistrationForm.tsx#L215) also says letters only.

The server independently enforces the same old restriction in [`normalize_person_name`](../backend/src/x_insight/cases/patients.py#L77): after NFC it accepts only characters for which `isalpha()` is true. Both registration and demographic PATCH call that function, so changing only the browser would still result in a 422; changing only the server would leave registration blocked. The field error returned by the server also has the old capitalized wording. Registration displays server field messages directly; chart editing currently displays a general API error rather than individual field errors. The old behavior is specified in [plan §2.2](../project-documents/dev/plan.md#L54), [the user guide](../docs/user-guide.md#L58), and [backend tests](../backend/tests/http/test_patients.py#L273) that explicitly expect names with spaces, hyphens and apostrophes to fail. This is a contract change, not evidence of a deployment-specific failure; no live incident was inspected.

## Smallest implementation plan

1. Define the same rule in the two existing validators, applied **after NFC normalization**: 1–100 Unicode code points, at least one Unicode letter, otherwise only Unicode letters, ASCII space (`U+0020`), hyphen-minus (`-`) and straight apostrophe (`'`); reject leading/trailing spaces and consecutive spaces. Preserve case and accepted spacing/punctuation, and keep the server's NFC storage behavior. The 100-code-point cap is a concrete sensible default; count code points in JavaScript (e.g. `Array.from(normalized).length`), not UTF-16 code units, to match Python `len`. Do not silently trim or collapse spaces. This interpretation allows punctuation at an edge or repeated punctuation, because the request imposes placement restrictions only on spaces. Noncomposing combining marks remain outside Unicode letter categories after NFC; keep that existing boundary rather than silently adding marks. Python and browser Unicode database versions can differ for recently assigned characters; use the same letter-category semantics and test representative characters in supported runtimes.
2. Update [`validation.ts`](../web/src/features/patients/validation.ts) and [`patients.py`](../backend/src/x_insight/cases/patients.py) in place, including their outdated contract comments. Give both field-specific, naturally worded messages, for example “Family name may contain letters, spaces, hyphens and apostrophes. Use 1–100 characters, with no leading, trailing or double spaces.” Use the equivalent Given name wording and same server field errors; retain the existing non-text handling and error structure. Update the registration hint to match. Do not introduce a shared cross-language package or dependency.
3. Update the obsolete rule in [plan.md](../project-documents/dev/plan.md#L54) and [user-guide.md](../docs/user-guide.md#L58) so future implementation and users are not directed back to the old rule. Preserve historical progress reports as history.
4. Update [backend patient HTTP tests](../backend/tests/http/test_patients.py): remove the three newly valid examples from the invalid cases; assert successful POST and stored NFC values for names with spaces, hyphens, apostrophes and non-ASCII letters, including `given_name: "Test"`, `family_name: "Patient Alpha"` as a full-name registration. Exercise both fields and PATCH through the existing shared validator. Assert 422 and the new field message for digits and other symbols, and cover empty, only punctuation, leading/trailing/double spaces, other whitespace, 100 versus 101 code points, decomposed input and supplementary-plane letters. Keep unrelated validation tests intact.
5. Add focused frontend validation tests using the existing `web/tests`/`test-web` runner with the same valid/invalid cases, including the code-point boundary and both field messages. Extend [registration browser coverage](../e2e/registration.spec.ts) to fill `Test` and `Patient Alpha`, register successfully, and verify returned/persisted names; also verify a digit and a symbol display the natural message and keep Register disabled. Use a unique patient ID. This proves the actual form and POST flow as well as both validators. Exercise an invalid server response/message separately where appropriate, since normal client gating prevents sending it.

## Change boundary and verification

Production changes should be confined to the existing patient-name validators and registration hint; documentation and the focused tests above are in scope. No schema migration is needed: patient name columns are `Text`. Do not alter identity/user names, search, identifiers, phone, age, chart editing UX, other workflows, existing records, or introduce dependencies. The shared server change naturally applies to chart PATCH; verify it without redesigning that form. Existing normalization and authentication, audit, revision and registration behavior must remain intact.

Run the focused backend patient tests (with the project's test database), `npm --prefix web run test-web`, the web build, and the registration Playwright test against a running app and test database in the configured browsers. Check both accepted and rejected values against each layer and inspect the returned error text and stored values. Report environmental blockers rather than claiming an end-to-end pass. No application code or tests were changed or run for this analysis.
