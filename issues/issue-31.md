# Issue 31: `make dev` does not start the generation worker

## Diagnosis

`make dev` starts the database containers, prepares schema and approved DDI data, and starts only the API and Vite ([Makefile](../Makefile)). It tracks those two process groups with `wait -n` and cleans them up on exit. The local Compose file supplies only databases, and `make stop` runs `docker compose down`; it does not control host processes. The installation guide explicitly requires a separate worker terminal ([installation guide](../docs/installation.md#6-start-the-background-worker)). This is a missing part of the local startup contract, not evidence of a queue defect. The original reason for leaving the worker separate is unknown.

The proposal path freezes inputs and enqueues the first eligible job in `start_generation_batch` ([snapshots.py](../backend/src/x_insight/reasoning/snapshots.py)). The API can therefore accept a job while no process consumes it. The existing `python -m x_insight.reasoning` entry point calls `poll_forever`, which invokes `run_once` to claim generation and local-calculation jobs ([entry point](../backend/src/x_insight/reasoning/__main__.py), [worker.py](../backend/src/x_insight/reasoning/worker.py)). Without a worker, eligible work stays queued; the ordinary `make dev` output does not identify a missing worker. The worker defaults to a five-second polling interval. A running process alone does not prove it can reach the database or process a particular job.

This diagnosis is based on source and existing handoffs, not a live reproduction. Provider configuration, job eligibility, maintenance mode and other failures can also prevent completion; starting a worker does not guarantee a successful proposal.

## Minimal implementation plan and exact scope

1. **Makefile:** after successful database preparation, start the existing worker with `cd backend && exec uv run python -m x_insight.reasoning`, in its own `setsid` process group, alongside API and Vite. Inherit the same exported environment, especially the effective `DATABASE_URL` and provider key settings. Include its PID in both cleanup loops and in `wait -n`; preserve cleanup of descendants and the exiting process's status. Do not start it before setup or add a separate target unless needed for this behavior.
2. **Makefile supervision and output:** identify which child exited (for example Bash `wait -n -p`, handling its status explicitly under `set -e`). If the worker exits unexpectedly, print a clear `worker is not running` diagnostic to stderr, return a failure even for an unexpected zero exit, and clean up API and web. Preserve existing nonzero server failure statuses. Normal Ctrl-C/TERM should clean up without a misleading crash warning. Announce that the worker is being started, but do not claim readiness merely because a PID exists. This detects process exit, not a live but stalled worker or a manually launched process outside this `make dev` session.
3. **Existing startup tests:** update `backend/tests/operations/test_startup.py` adapters and assertions to distinguish worker from API, check startup after setup and shared effective environment, and cover worker exit (including zero exit), diagnostic, failure status, and cleanup of sibling descendants. Update the existing API/web failure cases to cover worker cleanup, setup failure to exclude worker launch, and check signal shutdown. Keep the existing test harness; avoid new infrastructure.
4. **Current local instructions:** update `README.md`, `backend/README.md`, `docs/installation.md`, and Makefile help/header where they describe local startup or shutdown. Remove the mandatory separate worker command and explain that Ctrl-C ends the foreground API/web/worker groups while `make stop` stops Compose containers; `make stop` alone cannot stop an independently running foreground `make dev`. Update queued-job troubleshooting to inspect the foreground worker output and its database/maintenance state. Preserve relevant provider and MCP guidance. Adjust any other current instructions found by searching for the separate-worker requirement; leave historical progress records intact.

Do not change queue admission, worker execution, API/UI, production Compose, database schema, provider configuration, or clinical content. No dependency, health endpoint, persistent supervisor, auto-restart, or new monitoring service is needed for the requested local process lifecycle. Avoid asserting that process presence establishes functional worker health.
