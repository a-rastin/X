# Issue 27: autosave latency and safe step navigation

Status: analysis and implementation plan; no application changes or acceptance run. 2026-11-02.

## Finding

Diagnosis, C-SSRS and History all write the same full encounter draft through `web/src/features/encounters/useAutosave.ts`. `AUTOSAVE_DEBOUNCE_MS` is **1,000 ms**, restarted on each edit. A successful PATCH and a React render occur after that wait, so a visible, acknowledged Saved state within one second after the last edit is impossible on the debounce path even with an instantaneous server. The reported 4–6 seconds is **not yet explained by measurement**: it may include request, render, repeated input, or preview refresh time; the code alone does not establish their contribution.

The apparent lack of feedback has a separate confirmed cause: `EncounterPage.tsx` suppresses `DraftSaveStatus` for streamlined steps, including all three, except on failure or conflict. The existing status component already has accessible `Saving…`, `Unsaved changes…`, `Saved`, failure, and conflict states. The three assessment previews refresh from the server after a saved revision, which is a separate request from draft persistence; do not confuse preview completion with PATCH acknowledgment.

Navigation is not a reliable save barrier. Registration Diagnosis Continue uses `ensureSaved()` and checks the resulting revision and answers before its existing clinical confirmation flow. Most other Back, Continue, and step links change the hash first; the hash handler starts `flush()` without awaiting it. `flush()` returns immediately when a PATCH is already in flight and does not report failure. The parent keeps edits across an ordinary step switch, but leaving the encounter unmounts it; the in-app guard permits an explicit leave without saving. The hash, browser history, directory, top navigation, and logout paths require review. Browser unload has only a native warning, which the user can override; no web app can guarantee completion after a forced close or process termination. Explicit discard remains an intentional destructive action, distinct from navigation.

There is also an in-flight edit race to address as part of the shared fix: a successful `saveNow()` sets `saved` even if edits arrived after its snapshot, and a debounce callback coalescing with the in-flight request does not itself guarantee a second PATCH. A timer may be cleared by `flush()` while a save is in flight. Thus an old acknowledgment can temporarily or indefinitely misrepresent newer local changes; shortening the delay alone increases the chance of overlapping edits. The existing `editSeqRef`, `savedSeqRef`, and `ensureSaved()` provide the starting point, but render-synchronized refs and revision updates must be checked for same-turn edits and sequential saves.

## Measurement first

Before implementation, use a **disposable local test database and synthetic draft**, not a real patient or the existing service's unknown data. Record the environment, browser, sample count, and raw or median/p95 timings in the issue or progress log. For each of the three steps, measure from the last input event to PATCH start (debounce and scheduling); PATCH start to successful response (request); response to the first painted visible Saved indicator covering that exact edit (render); and last input to that indicator (end-to-end). Use browser performance marks, network timestamps, and a temporary test/dev-only observer or browser instrumentation; identify each attempt without recording answers, patient identifiers, request bodies, or credentials. Since the status is currently hidden, measure the existing save-state render via temporary instrumentation and separately document that the actual indicator is not displayed. Check the preview GET separately. Repeat idle and rapid input, including a delayed PATCH with an edit during flight. Record failures and conflict outcomes separately rather than treating them as timings.

Baseline established by source inspection: debounce **1,000 ms configured**; request time **not measured**; response-to-render **not measured**; end-to-end **not measured**; visible status on these steps **hidden**. A web server and an API port responded locally, but their data and configuration were not established as disposable, so no clinical draft was written and these timings cannot be claimed as measurements. The 4–6 s report remains unverified. Re-run the same measurements after the change, and write the numbers to the log. Choose a short debounce (start at **250 ms**) only after the baseline; adjust if the measured request and render budget requires it. The acceptance target is under normal local conditions, not a promise when the server or network is slow.

## Minimal implementation plan and exact scope

1. **Shared autosave (`web/src/features/encounters/useAutosave.ts`).** Shorten the measured debounce. Make the existing save state reflect the latest edit sequence synchronously: never report Saved until a 2xx covers all current edits; if edits arrive during a PATCH, serialize a follow-up PATCH on the acknowledged revision and do not lose its timer or a flush request. Reuse and, if necessary, repair `ensureSaved()` so it waits for in-flight and newer edits and returns an explicit outcome; prevent stale render-synced refs from causing old payloads or revisions. Preserve full-object PATCH, `If-Match`, idempotency, conflict and explicit reconciliation behavior; verify retries after a lost response do not reuse a key with a changed body. Do not silently retry a conflict or report a failed write as Saved. Audit all existing `flush`, `saveNow`, `ensureSaved`, `applyServerSnapshot`, and `applySavedSlice` callers before changing shared semantics, including diagnosis commands, medication strict saves, proposal review and signing.
2. **Wizard (`web/src/features/encounters/EncounterPage.tsx`).** Show the existing `DraftSaveStatus` on Diagnosis, C-SSRS and History, preserving its failure/recovery controls and one status element per page. Add a shared blur handler for editable controls in the wizard that requests an immediate save using the same serialized barrier; avoid issuing duplicate writes for clean state or ordinary internal focus changes. For Continue, Back and step links, await a successful barrier before changing step/hash; disable or coalesce repeated navigation while waiting and keep the user and local edits on the current step on failure or conflict. Retain the registration Diagnosis clinical check, snapshot verification and confirmation after the save; apply the shared barrier to follow-up as well. Handle browser back/forward and manually changed hashes without mounting a destination before the barrier completes; avoid recursive hash events and preserve requested destination only after success. Preserve the explicit discard workflow.
3. **Leaving the encounter (`web/src/app/navigationGuard.ts`, `web/src/app/App.tsx`, and wizard as needed).** Reuse the same asynchronous save barrier for in-app navigation, directory and logout, including links and browser history/hash changes. Keep the encounter mounted until success; on failure/session expiration/conflict retain edits and present recovery. Do not retain an in-app “leave without saving” override for ordinary navigation. Keep the native `beforeunload` warning for refresh, external navigation and tab close while unsaved; explain its browser-enforced limitation rather than promising a forced-close guarantee. Review route ordering so a hash change cannot unmount the draft before the guard acts. Explicitly test switching directly between different encounter IDs, not only paths outside `#/encounters/`.
4. **Focused tests (`e2e/autosave.spec.ts` and existing relevant diagnosis/history suites as appropriate).** Adapt the old test that accepts leaving with unsaved changes. Exercise each affected step with an immediate Continue and read back after reload; test blur and the visible `Saving…`/`Saved` lifecycle; assert the measured local end-to-end target of ≤1 s from the final edit to Saved on an acknowledged revision. Use controlled delayed PATCH responses to test edit-during-flight, repeated Continue, navigation before debounce, failure, 412 conflict, recovery, browser history/hash and in-app exit; verify no stale Saved, no premature step change and eventual persisted latest values. Retain diagnosis confirmation and follow-up behavior, and cover any shared caller whose assumptions change. Use deterministic response controls for race tests, with a real local stack for the timing acceptance; mocked response timing alone is not latency proof.
5. **Documentation.** Append the baseline and after-change timings, environment, test outcomes and remaining limitations to the relevant progress report and update the short index. Remove temporary measurement hooks unless they are already an appropriate test facility. No persistent logging of clinical data.

## Boundaries

Do not change backend APIs, schema, clinical questions, values, assessment calculations, preview semantics, authorization, revision fencing, conflict choices, proposal logic, or unrelated UI. Do not add dependencies, a second persistence system, generalized routing framework, or permanent performance telemetry. Touch other files only if the caller audit or a focused regression demonstrates they are necessary for the shared contract. No backend change is justified by the current evidence; investigate request time first if measurements show the PATCH itself consumes the budget.

## Acceptance checks

- On all three steps, the visible status reaches Saved for the latest edit within 1 s under measured normal local conditions, and only after the server acknowledges that edit. Report sample distribution and any outliers, not only the best result.
- Blur and Continue start saving promptly. Immediately leaving a step preserves the latest edit, including edits during an in-flight request, and reload/readback confirms it.
- In-app navigation waits for successful persistence; failure, expired session, and conflict preserve local edits and prevent ordinary navigation until recovered. Native unload prompts remain subject to browser/user override, and forced termination cannot be guaranteed.
- Existing clinical confirmation, author/revision checks, conflict resolution, intentional discard and other shared autosave consumers still work.
