# Issue 24: Versioned research disclaimer acknowledgement

## Finding

The observed behavior follows the existing implementation, rather than a failed save. The server's `_warning_for` returns the disclaimer only for physicians, on both login and `GET /me` (`backend/src/x_insight/identity/router.py`). The browser stores only the acknowledged user ID in `sessionStorage` and memory; logout and session expiry clear it (`web/src/features/identity/auth.tsx`). There is no server acknowledgement, version, or persistence across logins. `App.tsx` also explicitly restricts the gate to physicians. The old S05 handoff and `e2e/identity.spec.ts` explicitly describe and test this previous policy.

Administrators should be included under the requested rule: the Patients navigation is shared, and the patient directory and signed chart endpoints accept any active authenticated user (`backend/src/x_insight/cases/router.py`). Physicians and administrators are the two current roles. The existing disclaimer is server-supplied and the native modal already has a labelled alert dialog, initial focus, Tab handling, and prevented Escape. The app withholds route content while the gate is shown, preventing route dialogs from opening above it; keep that ordering. This is source analysis, not a live reproduction or proof of a reported dialog overlap.

## Minimal implementation plan

1. Add a nullable acknowledged-disclaimer-version column to `users` with a migration after the current head (`0028`); existing and new accounts start unacknowledged. Update the SQLAlchemy table and schema readiness version. Keep one current version constant beside the existing disclaimer text, and explicitly bump it whenever the wording changes. A single last-acknowledged version is sufficient; an acknowledgement history, timestamp, and new table are not required by this request.
2. Have login and `GET /me` use the stored user's version to return the existing warning text plus the current version when acknowledgement is required, for both current roles; return no pending warning when versions match. Keep text and version together as one authoritative server contract, and update TypeScript types and any affected mocks. Use the actual stored user, never a client-supplied user ID or login role.
3. Add one authenticated, CSRF-protected acknowledgement mutation under `/me`. The client submits the **displayed version**; the server accepts only the current version and writes it for the session user in the request transaction. If the version changed while the dialog was open, reject the stale acknowledgement and refresh the pending text/version; do not silently acknowledge text the user did not see. Repeated submission of the current version can succeed harmlessly. Do not change credential or physician profile revision merely to record this acknowledgement.
4. Replace the tab-storage acknowledgement logic in `auth.tsx` with the server state from login/`/me`; show the gate whenever the server says a warning is pending, regardless of role. Call the mutation from the existing dialog, retain it until a successful committed response, disable duplicate submissions while pending, and show an accessible retryable error on failure. Handle a stale-version response by loading and showing the new version, and avoid applying a late response to a different signed-in user. Preserve existing session and CSRF behavior and the native dialog's focus, Escape, scrolling, and route-content blocking. Remove obsolete `xi_warning_ack` logic; do not trust old tab entries as proof of acknowledgement.
5. Update backup/restore schema compatibility for the new migration in `backend/src/x_insight/operations/restore.py`: recognize the new schema wherever version-specific validation applies, preserve the column in new backups, and allow older backups to restore with the new nullable column unacknowledged. Check actual backup/restore serializers and their tests rather than assuming a schema-head bump alone is enough. Update schema-dependent expectations only where needed.
6. Update focused backend and browser tests and affected shared fixtures. Replace the tests requiring a warning on every physician login and no admin warning. Ensure shared administrator logins and `acknowledgeWarning` helpers account for persisted state without concealing a missing first-login dialog in dedicated acceptance tests. Update `docs/user-guide.md` only as needed to describe the new first-use/version behavior.

## Required verification

- With a real migrated database, both roles see the warning on their first login; acknowledge, sign out, and log back in with a fresh browser context: no modal. Refresh and a second account also demonstrate per-user server persistence and isolation. Existing accounts start pending after migration.
- Change the server version in a controlled test: both previously acknowledged roles see the new version again. A stale displayed version cannot acknowledge the new one; test login and `/me`, CSRF and unauthenticated denial, a failed save with retry, and no false local success. Verify a later login reflects the committed write.
- Exercise keyboard focus, Tab/Shift+Tab, Escape, and the action on the native modal, including a short viewport and a direct patient-route reload. Confirm route content and its dialogs cannot appear above the pending disclaimer. Check error announcements and retry by keyboard.
- Verify migration from the prior head, readiness, and new and older backup/restore behavior; run relevant identity, restore, and focused Chromium/Firefox tests. Check affected identity mocks and suites that create or reuse admin/physician sessions.

## Scope boundary

Change only the identity persistence/API and warning gate, the schema and necessary readiness/backup-restore compatibility, affected tests/fixtures, and the relevant user-guide sentence. Preserve disclaimer wording, existing patient authorization, login routing, clinical workflows, unrelated dialogs, visual styling, and existing data. This plan controls the UI workflow; it does not propose adding a new server authorization barrier to every patient API or building an audit history. No application code was changed or tests run during this analysis.
