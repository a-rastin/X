# Issue 17 — Attempt timing and generation failure visibility

Date: 2026-11-01  
Status: **Historical timing defect fixed in current source; focused isolated regression passed.** Deployment acceptance and the cause of the particular reported generation failure remain unknown.

## Executive finding

The wording “How it should be: Attempt `started_at` equals `finished_at`” conflicts with the following steps and the five-second acceptance criterion. This report interprets equality as **the reported defect**, not the desired behavior: a five-second attempt should have a five-second timestamp span, not equal timestamps.

The historical timing-defect root cause is established: `worker.run_once` captured the claim time once, then passed it as the completion clock after provider work. Both paths therefore recorded the claim time as the finish, yielding a zero-length attempt even after a five-second fake provider call. The existing fix, commit `2f58781`, is an ancestor of the current `dev` checkout. It avoids passing the captured claim time as a production completion clock; a deterministic `now` explicitly supplied by a test still intentionally fixes the clock. See [B21's reproduction and verification](../docs/BUGFIX_LOG.md#b21-attempt-timing-2026-10-31).

**The timing bug does not explain either why this specific generation failed or, by itself, why Status showed no alert.** No incident-specific attempt, deployment version, or database evidence was examined. A stale worker deployment, an old attempt, an explicitly injected test clock, or another bug are possible explanations for a current equal-timestamp observation; none is established here.

## Current implementation and acceptance

1. The worker captures the claim time in UTC and claims the job ([worker.py:80–109](../backend/src/x_insight/reasoning/worker.py#L80)). Claim inserts the attempt with `started_at=moment` and `finished_at=None` before provider work ([queue.py:1201–1215](../backend/src/x_insight/reasoning/queue.py#L1201)). `utcnow()` returns a timezone-aware UTC value ([contracts.py:107](../backend/src/x_insight/contracts.py#L107)).
2. The simple provider runs before `commit_job_result`, which receives the original optional `now`, not the captured claim moment ([worker.py:150–175](../backend/src/x_insight/reasoning/worker.py#L150)). With normal production `now=None`, completion obtains a fresh UTC time ([queue.py:1376](../backend/src/x_insight/reasoning/queue.py#L1376)), writes `finished_at`, and computes `elapsed_seconds` from that finish and the persisted start ([queue.py:1278–1288](../backend/src/x_insight/reasoning/queue.py#L1278), [queue.py:1530–1549](../backend/src/x_insight/reasoning/queue.py#L1530)).
3. The bounded path also passes the original optional `now` to the coordinator ([worker.py:133–147](../backend/src/x_insight/reasoning/worker.py#L133)). Failure uses the shared queue completion path ([coordinator.py:722–748](../backend/src/x_insight/reasoning/coordinator.py#L722)); successful completion resolves UTC after the pipeline and stores the span ([coordinator.py:1223](../backend/src/x_insight/reasoning/coordinator.py#L1223), [coordinator.py:1375–1389](../backend/src/x_insight/reasoning/coordinator.py#L1375)).
4. The existing [five-second regression](../backend/tests/worker/test_attempt_timing.py#L18) sleeps in a fake adapter, reads the persisted attempt, requires a 4–6 second span, compares `elapsed_seconds` to it, and checks UTC. It covers simple success and failure plus bounded-path failure. The historical B21 record reports **3 passed**. A subsequent focused rerun also passed; bounded-path success and the full backend suite remain untested in that rerun (see evidence below).

The timestamps measure **a job attempt from claim through completion**, not precisely one provider HTTP exchange: preparation, post-processing, multiple HTTP exchanges or a resumed stage may be included. Changing them to provider-call-only timestamps would change their existing meaning and is not needed for the stated five-second test. Some exceptional stale/lease-expired completions have their own paths; do not claim that all such paths populate `elapsed_seconds` without separate verification.

## Why failure can be hard to see

This is a separate, source-confirmed visibility limitation, not proof of the incident's root cause. Bounded failures pass an empty result to queue completion ([coordinator.py:737–743](../backend/src/x_insight/reasoning/coordinator.py#L737)); safe error details are recorded in the attempt ledger and structured warning ([queue.py:1519–1567](../backend/src/x_insight/reasoning/queue.py#L1519)). The public job shape exposes `result` but not the job diagnostics or attempt ledger ([queue.py:592–620](../backend/src/x_insight/reasoning/queue.py#L592)). The proposal panel looks for `job.result.error_code`, so a bounded failure can show the attempt count and generic “Later questions wait” rather than its actual error ([ProposalReviewPanel.tsx:179–205](../web/src/features/reasoning/ProposalReviewPanel.tsx#L179)). Existing private logs and audits can contain safe classifications; do not expose provider responses, credentials, exception messages, patient projections, or lease tokens.

## Why Status can say “No active alerts” during failure

The [status alert function](../backend/src/x_insight/operations/status.py#L285) has four specific conditions: queued generation job age over five minutes, leased job heartbeat age over two minutes, at least two provider-auth attempt codes in the last 24 hours, or backup staging disk usage over 80%. It does **not** alert on every failed generation or on the general provider failure count. For example, a terminal timeout or invalid-response failure with no qualifying queue, heartbeat, repeated-auth or disk condition can legitimately return an empty alert list. The auth count uses attempt **start** timestamps in the last 24 hours; equal start and finish timestamps alone do not suppress a qualifying auth alert. The queue age query includes queued jobs without filtering `next_eligible_at`, despite its “eligible” alert text. The Status page displays the returned alert list and separate provider counters; it is not a guarantee of successful generation ([StatusPage.tsx](../web/src/features/admin/status/StatusPage.tsx#L222)).

Whether the product should create a new failure alert, its threshold and its clearance behavior are not specified by the timing acceptance; inventing an alert policy or conflating one failure with total system failure would expand this issue. The reported particular alert state has not been reproduced.

Distinguish historical rows from attempts created by the current worker. Do not change production data or assume this checkout is deployed.

For any rerun, use project dependencies and an explicitly isolated disposable `TEST_DATABASE_URL`: the fixture migrates and truncates tables, so never point it at a real application database. Record actual output. An up-to-date deployment with this fix requires **no timing implementation change** for the covered paths.
3. **Only if the test fails or a current deployed attempt reproduces a timing defect**, trace that exact execution path and all callers. Correct the smallest shared clock/completion boundary: capture the UTC start before work, resolve a fresh UTC finish after work when no test clock is injected, and compute the elapsed span from the same persisted start and finish. Preserve fencing, transaction behavior and deterministic explicit clocks. Extend the existing timing test only for the proven uncovered path, then rerun it.
4. **Investigate the reported generation failure separately** using existing author-scoped batch status, safe attempt ledger/audit and worker structured logs. Record the safe error class/code, stage and attempt timestamps, and distinguish an old incident from a new test. If access or evidence is unavailable, report the blocker; do not infer a provider cause.
5. **Visibility follow-up, if desired:** the smallest targeted fix for the independently established UI gap is to expose only an allowlisted safe last error code through the existing author-authorized batch job contract and display it in the existing failure message, with a focused backend and UI regression. Verify ownership, serialization and all consumers before choosing the exact existing field; never expose arbitrary diagnostics. This is additional to the stated timing acceptance. For Status, first agree on whether to clarify that “No active alerts” means only the existing checks or to add a new explicitly specified failure alert; implement neither a threshold nor a broad alert redesign by assumption.
