# Issue 28: Continue and Register action semantics

Status: analysis and implementation plan, 2026-11-03. No application changes or runtime acceptance checks were made.

## Finding and root cause

The shared wizard pager in `web/src/features/encounters/EncounterPage.tsx` renders ordinary Continue transitions as `<a href=...>` with button styling (around lines 930–938). `followStepLink` changes the hash for an ordinary click, so these controls expose the **link** role and do not provide native Space activation or disabled-button semantics. The shared CSS makes links and buttons look alike, which does not change their accessibility role. This is a confirmed source-level cause; the reason the original implementation chose links is not established. Registration Diagnosis → PANSS is already a native button because it must save, evaluate and potentially ask for confirmation before navigating.

The report's Register claim does not match the current registration submit: `web/src/features/patients/RegistrationForm.tsx` already renders a `type="submit"` button, disabled when `!clientValid || busy`, and submits through the form handler. Its visible and accessible name is **Register patient**, changing to **Registering…** while busy. The directory's **Register new patient** is an anchor to `#/patients/new`, a navigation destination; it is not the submission action. The saved registration step later has a Continue link to Diagnosis, not another registration submit.

Current Continue names are **Continue to [step]**, or **Checking diagnosis…** while the guarded check is running. Therefore an exact accessible-name query for `Continue` or `Register` will not match even the existing buttons; some query libraries do substring matching by default, others default to exact matching. The plan below meets the literal names without an `aria-label` that hides the visible words from the accessible name. The busy-state names intentionally change while work is in progress.

## Minimal implementation and complete change scope

1. In `EncounterPage.tsx`, change only the unguarded forward pager anchor to `<button type="button">` with the same `id` and `xi-btn xi-btn-primary` classes. On activation assign `window.location.hash = encounterStepHash(encounterId, nextStep.id)`, as the current ordinary link handler does; preserve the existing hash-change save guard, failure handling, step focus and history behavior. Do **not** call `goToStep` for this path: it also sets React step state immediately and could bypass the guard's wait. Native buttons supply Enter and Space; do not add keyboard handlers. Preserve the existing guarded diagnosis handler, its disabled condition, confirmation and focus restoration. Give both forward buttons visible text `Continue` in their idle state; retain `Checking diagnosis…` during the check. Do not invent a disabled condition for otherwise available transitions.
2. In `RegistrationForm.tsx`, keep the existing native submit, handler, validation and `disabled={!clientValid || busy}`; change only its idle visible text from `Register patient` to `Register` so the exact accessible-name acceptance check succeeds. Retain `Registering…` while busy. The form's accessible name and wizard step labels remain `Register patient`.
3. Update the existing affected Playwright selectors in `e2e/registration.spec.ts`, `e2e/autosave.spec.ts` and `e2e/ddi-fresh-install.spec.ts` (and any other selectors found by searching at implementation time): target the new button role/name for the submit and forward pager, preserving the directory navigation link query. Update stale comments/assertions in `e2e/diagnosis.spec.ts` that describe the follow-up Continue as a link. Existing `#wizard-continue` selectors need no mechanical change. Keep other registration, autosave and diagnosis tests intact.
4. Add focused browser coverage in the existing relevant suites: exact role/name checks for idle `Continue` and `Register`; activate each with Enter and Space in separate fresh states and verify the intended transition or single registration submission. Check registration disabled with invalid fields and while a controlled submission is pending, and that activation cannot submit then; check guarded diagnosis disabled until ready and while checking, and its confirmation/cancel behavior. Cover ordinary forward navigation with a delayed or failed save to verify the hash guard still waits and preserves the draft; retain follow-up behavior and browser Back/forward. Check the same visual classes and focus behavior. Run the affected registration, diagnosis and autosave tests in Chromium and Firefox against a disposable test stack.
5. Run axe on the registration form and representative ordinary and guarded Continue screens, in relevant enabled/disabled states, comparing before and after so no **new** violations are introduced. The manifests currently contain no axe integration; use an existing available axe runner if one is present in the actual test environment, otherwise add only the minimum test-only axe integration (for example `@axe-core/playwright` and its lockfile change), not a production dependency. Record baseline and after findings, scope, and test results; do not silently ignore new violations.
6. Append implementation results and unresolved verification to `project-documents/dev/progress/s07.md` and add a short index entry in `project-documents/dev/progress/README.md`.

## Boundaries and acceptance

- Back, step-list and directory links remain anchors: they identify destinations. Do not change routing, autosave, API, backend, clinical content, validation, styles or dependencies except the focused test-only axe tool if needed. Reuse existing button CSS; adjust CSS only if an actual visual difference is demonstrated.
- Preserve issue 27's current hash navigation save barrier, including its known incomplete browser-history and latency verification; this issue does not implement or certify that separate work. Preserve the diagnosis clinical guard and registration's one-submit protection.
- In the idle states, exact `getByRole('button', { name: 'Continue', exact: true })` and `getByRole('button', { name: 'Register', exact: true })` succeed on their respective screens. Verify native keyboard activation, actual disabled behavior and role exposure, unchanged navigation/registration outcomes, and no new axe violations. Do not claim acceptance until the browser checks and axe comparison have run.

Evidence is static source and existing test inspection only; no reproduction, visual comparison, keyboard run or axe baseline was performed in this analysis.
