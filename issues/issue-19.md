# Issue 19 — Failed-run transparency and bounded loading

Date: 2026-11-01  
Status: **Analysis and implementation plan; not implemented or verified against the tester's deployment.**

## Problem and scope

A tester reports that generation failed, the Status page said “No active alerts,” and transparency stayed at “Loading persisted transparency…”. The actionable acceptance in this issue is the transparency panel: a failed run with no stored transparency must show **“No transparency data because this run failed” within 2 seconds**, and a blocked review endpoint must produce an error with a working retry instead of an indefinite loader. The “How it should be” sentence repeating the loading text conflicts with the explicit steps and acceptance; this plan follows the latter.

The incident's particular generation failure, request outcome and deployed version are unknown. The following source analysis identifies defects capable of producing the symptom; it does **not** prove which occurred in that incident.

## Root cause and current behavior

1. Opening a question's transparency calls `getQuestionReview(runId)`, issuing `GET /api/v1/question-runs/{run_id}/review` ([panel](../web/src/features/reasoning/ProposalReviewPanel.tsx#L848), [API](../web/src/features/reasoning/api.ts#L459)). The panel sets a per-run loading entry and waits for the request. The fetch **and response body read** have no deadline or abort signal ([api.ts](../web/src/features/reasoning/api.ts#L373)); a connection or body that never settles therefore leaves the loading state indefinitely. Closing and reopening also reuses that loading cache entry ([panel](../web/src/features/reasoning/ProposalReviewPanel.tsx#L850)). A hanging request is a code-supported explanation, not an observed incident trace.
2. A failed original run normally has no persisted successful baseline. The author-scoped review endpoint returns HTTP 200 with `baseline: null`, `transparency: null`, and `adjustable: false`, not a recomputed result ([router](../backend/src/x_insight/reasoning/router.py#L397); [worker test](../backend/tests/worker/test_single_question.py#L427)). On a timely response the UI already exits loading, but shows a generic future-completion explanation instead of explicitly saying the run failed ([panel](../web/src/features/reasoning/ProposalReviewPanel.tsx#L876)). Thus failure itself does not automatically cause a permanent spinner.
3. Settled request failures already show an error and retry control, but the retry callback uses the expand/collapse toggle. Since the panel is already open, the first click closes it rather than issuing another request ([callback](../web/src/features/reasoning/ProposalReviewPanel.tsx#L1106), [toggle](../web/src/features/reasoning/ProposalReviewPanel.tsx#L848)). A cached null result can also remain unavailable if the same run later gets a successful baseline, because non-error entries are reused.
4. A question's generation failure is derived from its matching batch job and can include attempt count and safe error code; its generation retry is distinct from transparency retry ([panel](../web/src/features/reasoning/ProposalReviewPanel.tsx#L179), [retry](../web/src/features/reasoning/ProposalReviewPanel.tsx#L1269)). Do not infer per-question failure from the review endpoint's `job`: that compatibility field refers to the batch's first job, which may be for another question ([router](../backend/src/x_insight/reasoning/router.py#L454)).

### Why Status can report no alerts

Status is a separate operational snapshot, not a list of all failed generation jobs. Its existing conditions are old queued work, stale heartbeats, repeated provider authentication failures, and high disk use ([status.py](../backend/src/x_insight/operations/status.py#L285)); other failures may produce zero alerts, rendered as “No active alerts” ([StatusPage](../web/src/features/admin/status/StatusPage.tsx#L233)). This explains the possible mismatch, not the particular incident. The stated acceptance does not define a new alert threshold, scope or clearing policy. Do not invent one in this fix; treat broader Status alerting as a separate product decision. See [issue 18](issue-18.md) for existing failure-audit visibility and its verification limits.

## Minimal implementation plan

1. **Keep the existing lazy persisted-review GET.** Split the current toggle from a small loader so opening fetches as before and the error's retry invokes the loader directly without collapsing. Preserve existing authorization/session-expiry handling and existing valid persisted results; do not infer success or generate transparency locally.
2. **Bound this review request, including body consumption**, with a native `AbortController` and a deadline short enough to meet the two-second acceptance; use 1,500 ms initially to leave rendering margin. Pass an optional abort signal through the existing reasoning request helper and `getQuestionReview`, using it only for this transparency caller. Clear the timer on every outcome. Distinguish timeout from session expiry and present a safe actionable error and retry; HTTP/network/body-read errors use the same error path. Cancel or otherwise guard in-flight requests on unmount/run replacement and prevent an older aborted request from overwriting a newer retry. Do not implement a bare `Promise.race` that leaves the fetch and body read running. A short deadline can reject slow but healthy requests; the retry is the recovery and the value should be revisited only with measured evidence.
3. **Render the correct empty state only on a successful null review for a question known to have failed.** Use the existing per-question display/job state, not the review response's first-job compatibility field. Preserve a successfully persisted transparency result even if a later job failed. For pending, skipped or clarification cases retain an honest neutral unavailable explanation; never call a request failure an empty result. Continue requesting review even for failed runs, so a blocked endpoint produces the required error rather than falsely claiming there is no stored data. Invalidate or refetch a cached null result when the corresponding run gains a baseline, and do not retain stale loading entries across replacement/retry. Keep completed successful data cached.
4. **Add focused browser regressions** in the existing proposal review/failure tests: failed job + prompt successful null response shows the failure-specific empty state within 2 seconds; a deliberately unresolved GET times out to an error and a single retry succeeds without closing; settled HTTP/network error likewise retries in one click; pending/null is not labeled failed and becomes available when the same run receives a baseline; completed persisted results remain correct. Include a delayed response/body or equivalent and a late/aborted response check so neither indefinite body reads nor stale completions can overwrite the latest state. Use controlled fixtures, and keep the existing worker null-result test as backend contract evidence rather than changing the endpoint. Run affected Playwright cases in Chromium and Firefox and the web build; report actual results and any environmental blockers. Measure the two-second bound from opening the panel under a prompt mock, not from generation completion.
5. After implementation, update this report and the relevant progress handoff with actual changes and verification. For deployed acceptance, separately verify the running version and reproduce with authorized non-sensitive test data; do not assert the tester's incident cause without its request evidence.

## Complete change boundary

| Area | Changes permitted |
| --- | --- |
| `web/src/features/reasoning/ProposalReviewPanel.tsx` | Transparency loading/retry, failed-versus-neutral null rendering, cache invalidation and lifecycle/stale-request safety only. Preserve question generation retry, sign-off gating, persisted data and existing accessible status/error roles. |
| `web/src/features/reasoning/api.ts` | Optional request abort signal and optional signal argument for `getQuestionReview`; retain existing behavior for all other callers including CPT review, freshness and signing. |
| `e2e/proposal-review.spec.ts` and/or `e2e/failure-recovery.spec.ts` | Extend existing fixtures and focused tests only as needed for the above cases. Mocked browser checks prove UI/request behavior, not a live worker or deployed endpoint. |
| Documentation | Update this issue and the relevant progress report/index after implementation. |

**Do not change:** backend review contracts or database schema, worker/generation retry budgets, provider behavior, audit or Status rules, clinical logic, permissions, unrelated UI, or add dependencies. Do not use `review.job` as the failed question's job, expose raw provider data, or conflate timeout with a successful empty response. If an acceptance test reveals a separate required change, identify the evidence before widening the boundary.
