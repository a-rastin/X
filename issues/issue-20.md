# Issue 20 — Make generation failures visible on Status

## Finding and evidence

**The reported display is possible with the current code; the particular incident and deployment have not been inspected.** Status evaluates four conditions: old queued jobs, stale heartbeats, repeated provider authentication failures, and high backup-disk use. It never evaluates `generation.run.failed` events. Consequently repeated terminal failures such as timeouts or invalid responses can coexist with an empty alert list, which the page renders as “No active alerts.” See [status aggregation](../backend/src/x_insight/operations/status.py#L285) and [alert rendering](../web/src/features/admin/status/StatusPage.tsx#L234). The 24-hour provider failure counter counts **attempts**, not terminal run failures, and is not a general failure alert. Three failed attempts for one run produce one run-failure event, as the [worker regression](../backend/tests/worker/test_failure_details.py#L184) demonstrates.

The two timeouts have different owners. [`INFERENCE_TIMEOUT_SECS = 30`](../backend/src/x_insight/models/inference.py#L105) bounds local Bayesian inference; the Status API places it in `inference.limits.inference_timeout_seconds`. The UI prints raw limit keys under the generic “Inference limits” heading. The provider deadline is already returned independently as `provider.timeout_seconds` and displayed under “Provider” ([status.py](../backend/src/x_insight/operations/status.py#L209), [StatusPage.tsx](../web/src/features/admin/status/StatusPage.tsx#L296)). B01 resolves it from the latest saved setting, then the environment, then the 300-second default ([installation guide](../docs/installation.md#L314)). Existing runs can use a pinned older revision, so the Status value is the **current setting**, not necessarily the deadline used by the last failed run. The report of 30 seconds is not evidence of a provider deadline or the cause of the incident.

Run-failure audit details contain the job ID, attempt index, and error code, **not** `failure_class` ([coordinator](../backend/src/x_insight/reasoning/coordinator.py#L793)). Provider attempt records hold the class ([tables](../backend/src/x_insight/reasoning/tables.py#L182)); `generation.attempt.failed` records it too. Some failures or historical records may lack an attempt/class. Audit details also include patient identifiers, so the status response must not copy the event payload.

## Minimal implementation plan

1. Extend the existing read-only status aggregation in [status.py](../backend/src/x_insight/operations/status.py) with one global rule using the existing audit table and `generation.run.failed` / `generation.run.success` operation constants. Default to **at least 3 terminal run-failure events within the last 30 minutes**, counted since the most recent success in that window. Make count and window deployment-configurable with validated positive settings and defaults; follow existing configuration conventions. Define the window inclusive at its start and bounded by snapshot time. A success resets the count; three *new* failures are required to re-alert. An alert also expires when the rolling count falls below the threshold. The scope is global, matching the existing admin operational snapshot; a successful run anywhere clears this rule, not unrelated alerts. This is an explicit interpretation of the requested clearing behavior. Query the bounded events in a deterministic order using the existing audit `(occurred_at, id)` ordering; UUID tie-breaks are deterministic but do not prove commit order for equal timestamps. Keep the calculation read-only and effective across process restarts.
2. For the latest counted failure, obtain the matching attempt by its audit job ID and attempt index, and expose only an allowlisted known `failure_class` such as `timeout`, `disconnect`, `http_status`, `parse`, or `other`; use `unknown` if absent, invalid, or no corresponding attempt exists. Do not borrow a class from another job or an earlier attempt. Return a safe alert name, count, window, and class in the existing `alerts` array; let the existing card render them with a readable “Last failure class” label. Never expose audit details, IDs, provider text, exception messages or clinical data. Confirm actual class values against the adapter before finalizing the allowlist. No migration or historical audit rewrite is needed.
3. In [StatusPage.tsx](../web/src/features/admin/status/StatusPage.tsx), label the existing provider section and row **AI provider** / **AI provider timeout (current setting)**, and label the inference section **Bayesian inference** with a human-readable **Bayesian inference timeout** in seconds. Preserve every other existing limit and metric; do not duplicate either timeout. Keep the API's existing keys and use its existing separate values. Update the status client comments/types only if needed for the safe alert field.
4. Add focused tests in [test_ops_status.py](../backend/tests/http/test_ops_status.py): fewer than three run failures, threshold reached, success clearing, three fresh failures re-alerting, rolling-window expiry and boundary, configurable values, deterministic equal-time behavior, and latest matching class / missing or unsafe class fallback. Exercise the real status endpoint and audit/attempt data, distinguishing three terminal runs from three retries, preserving admin authorization and no-leak checks. Extend [status.spec.ts](../e2e/status.spec.ts) to verify the two separately labelled values and the alert class and cleared state on refresh; use controlled status responses for the UI if appropriate, alongside the real backend test. Retain coverage of the existing B01 timeout resolution and older alerts. Update the operator status/alert documentation with the defaults, settings, global reset/expiry semantics, and current-versus-pinned timeout distinction.

## Change boundary and verification

Expected production changes are limited to status aggregation/configuration, the Status page and, only if necessary, its alert type. Tests and the relevant operator documentation are in scope. Reuse the existing audit and attempt tables, endpoint, polling and provider timeout resolution. Do **not** change generation, provider retry behavior, clinical workflows, audit creation/history, database schema, authentication, other alerts, unrelated UI, or add dependencies. If implementation discovers the existing event linkage cannot supply a class, preserve the `unknown` fallback rather than broadening the worker or audit contract without evidence.

Run the focused backend status and provider-timeout tests, the relevant status browser test, and the project's applicable formatting/type checks. Verify with three distinct forced terminal run failures and then one successful run, checking the real endpoint and page after refresh (or the existing visible-tab poll, about 30 seconds); ensure an unrelated active alert may remain after this rule clears. No code or tests were changed or run during this analysis; incident cause and deployed acceptance remain unverified.
