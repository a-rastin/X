# Issue 25 — Physician-facing question labels and advanced details

## Finding and root cause

The checked-in UI mixes workflow identifiers with presentation. Question keys are needed for joins, requests and frozen records, but the rendering layer also prints them as names; no common presentation map covers all of its branches. The batch header renders its identifier and fingerprint unconditionally. This is directly supported by the source, not a confirmed observation of a deployed instance. No application or test code was changed or executed for this analysis.

- `web/src/features/reasoning/ProposalReviewPanel.tsx:283` puts keys into signing and incomplete-workflow messages. At `:1265` it displays `batch.batch.id` as “Run” and at `:1271` the fingerprint. At `:1323`, `:1359`, `:1373`, `:1451`, `:1666` and `:1685` it renders keys in question status, actions, transparency, completed sections and skipped sections. Raw keys also appear in table accessible names at `:1486` and `:1573`.
- `web/src/features/reasoning/CptReviewPanel.tsx:427` and `:438` use keys in accessible names and button text. Expanded review exposes acceptance IDs and a shortened input hash at `:949`; other result/reuse and acceptance-history details contain IDs at `:854` and `:1026`. `web/src/features/plans/SignPanel.tsx:120` includes keys in signing errors and at `:187` shows the snapshot ID and hash after signing.
- Readiness produces a mechanical label via `key.replace("_", " ").capitalize()` in `backend/src/x_insight/reasoning/readiness.py:41`. `ProposalReadinessSummary.tsx:56` and `:76` trust that label; `HistorySection.tsx:525` trusts it or independently humanizes the key. Thus `aggression_clozapine` becomes “Aggression clozapine”, not an intentionally written clinical heading. A blocker can also fall back to that server-generated label (`readiness.py:158`). History is an Assessment step, so it is part of the requested check.
- Expanded transparency includes baseline IDs and effective hashes (`ProposalReviewPanel.tsx:1469`, `:1475`, `:1605`), plus arbitrary persisted provenance at `:1614`, which can contain identifiers or hashes. Simply hiding the header fingerprint does not satisfy acceptance when normal clinical transparency and CPT review are opened.

The app uses a pinned question bundle and keeps technical references for freshness, retry, review, acceptance and signing; these operations still need the original keys and IDs. The label defect is a presentation problem; the original historical reason for exposing identifiers is unknown. The previous transparency work retains bounded requests and clinical review information ([S48 handoff](../project-documents/dev/progress/s48.md#follow-up-2026-11-02--issue-19-implemented-and-verified-on-the-preview-harness)).

## Smallest implementation plan

1. Add one frontend question-label map and a small lookup helper shared by the relevant components. Cover all 11 keys from the registration and follow-up bundles selected by `content/bundles/active-release.json`: `pharmacotherapy`, `high_suicide_clozapine`, `lai_indication_choice`, `aggression_clozapine`, `established_case_clozapine`, `tardive_dyskinesia`, `akathisia`, `parkinsonism`, `acute_dystonia`, `no_improvement_clozapine`, and `continue_or_adjust`. Use clear, clinically meaningful wording, including “Pharmacotherapy” and an intelligible phrase for aggression/clozapine rather than mechanical title casing. These are display labels, not changes to reviewed clinical content. For unknown keys, replace separators and normalize whitespace/case to a readable phrase; warn in development without logging patient data. Never throw or break historical/unknown runs.
2. Use that helper for visible text and accessible names throughout the Proposal status, retry/transparency controls, complete/skipped sections, pending/clarification/failed messages, CPT review and sign-blocking errors. In `ProposalReadinessSummary` and `HistorySection`, derive the displayed question heading from its key through the same helper instead of trusting the mechanically generated `question_label`; where a blocker label is specifically the server's question-label fallback, use the mapped label while retaining genuine field definitions. Preserve raw keys in React keys, `id`, `data-testid`, API calls and sorting. Check any displayed server-provided reasons for embedded keys before considering the work complete; handle actual structured key fields at presentation boundaries rather than globally rewriting clinical text.
3. Add a native, initially closed `<details><summary>Advanced details</summary>…</details>` disclosure to Proposal review, with its state shared with nested review/signing content if needed. Show the batch ID and fingerprint there, as well as technical IDs and hashes otherwise exposed by expanded transparency, CPT acceptance/history/reuse, and sign success. Include raw question keys there if diagnostic access is useful. Keep status, freshness, explanations, probabilities, clinical transparency and acceptance actions accessible without opening it. Treat arbitrary provenance as advanced content so unknown fields cannot leak identifiers; ensure all occurrences of an effective hash, including the duplicate result line, are gated. The disclosure is a presentation control, not authorization; default to availability for the existing authorized physician users. Restricting it to admins is optional and requires an owner decision and real authorization enforcement if confidentiality is intended; do not add role policy in this fix by default.
4. Add a small automated completeness check that reads the two **currently active bundle paths** from `active-release.json`, extracts every `question_key`, and checks membership and nonempty labels in the actual frontend map without invoking its fallback. A hardcoded duplicate list alone cannot catch a newly added bundle key. Include a test proving a missing key fails, plus fallback and development-warning checks. Preserve the fallback for older or externally supplied keys that cannot be enumerated by the current bundle test.
5. Extend existing focused browser coverage (not a new framework): exercise registration and follow-up readiness/History, plus pending, failed, clarification, skipped, completed, expanded transparency, CPT acceptance and signed-success states using controlled data. Assert human labels in visible text and accessible names, and assert no fixture keys, UUIDs or hashes in the default visible content, including after ordinary clinical disclosures are opened; opening Advanced details reveals the expected exact identifiers/hashes, and closing it hides them again. Verify labels and unknown-key fallback independently of DOM attributes, which intentionally retain identifiers for stable selectors. Retain existing review retry/timeout and acceptance/signing behavior, and update text-based tests whose expected labels change. Run the focused tests, `cd web && npm run test-web`, `npm run build`, and the relevant Playwright specs using the existing project setup.

## Change boundary and handoff

Expected application changes: the shared frontend label map/helper; `ProposalReviewPanel.tsx`, `ProposalReadinessSummary.tsx`, `HistorySection.tsx`, `CptReviewPanel.tsx` and `SignPanel.tsx` as needed to route display labels and the disclosure; focused existing test files and the completeness test. A small prop or context to share disclosure state is acceptable if necessary; do not introduce a general settings framework. Keep the disclosure closed on fresh entry and on remount; it need not persist across navigation. Use normal keyboard-accessible native disclosure semantics.

Do not change the backend API, database, workflow keys, reviewed bundles, generation, fingerprints, audit records, retry/polling, acceptance or signing contracts, or clinical recommendations. Do not remove clinical information or change the underlying data to achieve presentation hiding. Network responses, URLs, DOM IDs and test IDs can still contain technical identifiers: this request concerns the rendered and accessible physician interface, and the disclosure is not a security boundary. Backend readiness's existing `question_label` remains for API compatibility; physician-facing consumers use the common map. No dependencies, migration, redesign or role restriction are needed for the default solution.

The separate signed chart view (`web/src/features/plans/SignedView.tsx:122`, `:138`, `:304`) also renders question keys, snapshot/batch/proposal IDs and hashes, and the Medications DDI provenance disclosure contains a fingerprint (`DdiReportPanel.tsx:266`). They are adjacent physician-facing surfaces, but the stated acceptance names Proposal and Assessment; do not expand this change to signed chart or Medications without a scope decision. If either is considered part of the target screens, apply the same map and closed advanced disclosure there and extend the tests accordingly.

**Verification limit:** this diagnosis is based on source and existing handoffs, not a browser reproduction, production data, or a live provider. Implementation and acceptance are outstanding.
