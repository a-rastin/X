# Issue 26 — Explain changing readiness counts

## Finding and root cause

The checked-in Proposal readiness counter has a **dynamic denominator but no explanation that it can change**. It counts required inputs in the currently applicable workflow manifests, not a fixed questionnaire. When a History answer reveals or removes conditional inputs, both the applicable set and its count change. Existing Unknown defaults can also count as answers, so newly applicable inputs can increase both numbers immediately. A saved revision refresh can make several changes appear together. These mechanisms explain the reported jumps in principle; the exact reported sequence has not been reproduced against a running deployment.

- `backend/src/x_insight/reasoning/readiness.py:42` obtains each question’s currently applicable required paths through `snapshots.applicable_required_fields`; `snapshots.py:544` filters them using `workflow_release.py:407` and each field’s `show_if`. The loop at `readiness.py:50` counts answers only within that same list, at most once per entry, and lines 111–125 sum the per-question values. Unknown is a permitted explicit answer in this accounting; missing context may instead be execution-ready without being answered. Counts are per required input in a workflow question, including non-History inputs such as C-SSRS, not necessarily unique visible History controls.
- `web/src/features/reasoning/ProposalReadinessSummary.tsx:49` prints the server’s answered and required counts together, then a separate execution-ready count. It is shared by History (`HistorySection.tsx:652`) and Proposal (`ProposalReviewPanel.tsx:1118`), and currently does not explain changes in the required set. History refreshes its saved preview after acknowledged saves (`HistorySection.tsx:331`) and flags pending local changes (`:651`); Proposal uses a saved revision and suppresses stale or unsaved readiness. These distinctions should remain visible.
- The existing `e2e/history.spec.ts:677` exercises lifetime exposure Yes followed by No/Unknown: the saved readiness total changes from 12 to 14 and back to 12 as dependent inputs become applicable and then are cleared. `e2e/proposal-review.spec.ts:390` already distinguishes 10/14 answered from 14/14 execution-ready. The separate Past medical history counter (`HistorySection.tsx:200`, `:452`, `:472`) also follows currently visible conditional core fields, including Unknown defaults; it is not the Proposal readiness total.

**Overflow evidence:** the reported sequence 8/12 → 13/14 → 14/14 does not itself exceed the denominator. In the checked-in calculations, answered is bounded by required for each server response and the core History numerator is filtered from its denominator. No source-level cause for an answered-greater-than-required value was established, and no live reproduction was performed. Do not invent a mismatch or hide one with a numeric clamp: if a focused test exposes an overflow, trace its actual source and fix the matching set/revision calculation.

Changing answers or saved information can also change the answered count.” This explains both directions, including a lower numerator when a previously answered dependent question disappears, without storing prior counts or changing clinical rules. Preserve the existing live region and uncertainty/blocker explanations.
