## What landed

Migrations 0019, 0020, and 0021. 0019 adds append-only `provider_settings`
with app-role SELECT and INSERT. 0020 makes the key columns nullable so
clear can store NULL. 0021 adds a `capability_status` check: `untested`,
`verified`, `failed`. `EXPECTED_SCHEMA_VERSION` is `0021`.
`SUPPORTED_APP_SCHEMA_VERSIONS` includes 0017 through 0021. A missing
`provider_settings` table is accepted only for app schemas 0017 and 0018.
`BACKUP_TABLES` lists `provider_settings` immediately after `users`. The
deployment key is not in the backup.

Routes on `/api/v1`: GET and PUT `/api-settings`, POST `/api-settings/test`,
GET `/api-settings/revisions/{revision}`. Admin session. Writes need CSRF.
`If-Match` is a quoted revision. Absent `If-Match` means no precondition. A
mismatch is 412 `STALE_REVISION`. Anonymous is 401. Physician is 403.

AES-GCM via cryptography 50.0.2, 12-byte nonce, no AAD.
`X_INSIGHT_PROVIDER_DATA_KEY` is base64 of exactly 32 bytes and stays
outside the database. `.env.example` documents it empty.

`X_INSIGHT_PROVIDER_ALLOWED_HOSTS` is a comma-separated exact-host list.
Empty fails closed, including no loopback exception. `.env.example`
documents it empty. Save checks http(s), no userinfo, and an exact hostname
match. DNS and special-use addresses are checked only on the capability
POST. Redirects are not followed. `post_json` in `reasoning/provider.py` is
the one HTTP POST (`follow_redirects` false). The allowlist is not inside
`BoundedProviderAdapter._post_once`.

`secret_action`: `unchanged`, `replace`, `clear`. The placeholder
`configured` is not stored. Clear stores NULL and GET shows `api_key`
absent. Every save sets capability to `untested`. `replace` and `clear`
call `cancel_active_generation_jobs` (queued or leased generation jobs, all
encounters; `local_calculation` jobs stay) and return `affected_runs`. Rows
are not deleted. `unchanged` and the first save do not cancel.

POST `/api-settings/test` appends a revision. Verified only when the
upstream returns 200 JSON with `ok`, `supports_tools`, and `supports_json`
true. Otherwise failed. Diagnostics are fixed strings, never the upstream
body or the key. Saving is not verification.

GET of an older revision stays available after replace and clear. That
route does not decrypt. Audit operations `api_settings.save` and
`api_settings.test` do not record the raw key or ciphertext.

Admin page `#/provider-settings`, nav label Provider. Shows configured or
absent, and untested, verified, or failed, as text. Password input. Replace
and clear are explicit. GET 404 is an empty unsaved form. A physician sees
"Administrator access required." and no Provider link.

## Follow-up 2026-10-18 — CSRF failure diagnosis

Static diagnosis only; no application code changed and no tests ran. Provider
save reaches the admin mutation gate before any provider URL, model, API-key,
deployment-key, or allowlist validation. The reported `403 FORBIDDEN` / `CSRF
validation failed.` therefore means the authenticated session cookie was
present, but `X-CSRF-Token` was absent or did not match that session.

The frontend keeps the CSRF token in tab-local `sessionStorage`, while the
HttpOnly session cookie is shared across same-browser tabs. Startup restores
authentication through `GET /me`, whose response does not contain a CSRF token.
Consequently, a new tab can appear authenticated from the shared cookie but
have no CSRF token, and logging in from another tab can replace the shared
cookie while leaving this tab's token stale. Signing out and back in in the tab
is the immediate recovery. The product fix should re-synchronize a session's
CSRF token during authenticated startup (with a regression check covering a
cookie-authenticated tab that lacks or holds a stale tab-local token). The open
issue is specified in
[`issue-csrf-session-desynchronization.md`](../issue-csrf-session-desynchronization.md).

## Follow-up 2026-10-18 — synchronize CSRF with the shared session

Fixed the diagnosed mismatch without weakening the backend CSRF gate.
Authenticated `GET /me` now returns the token bound to the presented session
and is `private, no-store`. Startup adopts that token, 401 clears it, and the
frontend keeps it in origin-shared `localStorage` and reads it at mutation time,
matching the scope and replacement behavior of the shared HttpOnly session
cookie. Synchronization also removes the obsolete tab-local copy.

Verification: focused identity backend suite 22 passed against PostgreSQL; web
production build passed; backend Ruff check/format passed. The provider
missing-token reload followed by save/test/clear passed in Chromium and Firefox.
The cross-tab replacement followed by a mutation from the first tab passed in
both browsers. Its first Firefox run timed out during a concurrent second login
but passed alone; the provider test in that combined run passed. Root TypeScript
checking remains blocked only by the previously recorded
`e2e/signing.spec.ts:848` TS2352. Full backend and browser suites were not run.
The issue document records the fix and evidence; no commit SHA is claimed.

## Follow-up 2026-10-18 — fake-IP capability check and failure color

Capability tests against allowlisted public hosts failed with `Resolved address
is not an allowlisted IP` because this machine's resolver returns
`198.18.0.0/15` (RFC 2544 fake-IP). Python marks that range private, so the
check demanded the ephemeral IP on the host allowlist. `198.18.0.0/15` is no
longer treated as a special-use block. Loopback, link-local metadata, and
RFC1918 still fail unless that exact IP is allowlisted. A failed diagnostic
uses `xi-form-error` (urgent), not green `xi-status`.

Verification: `test_fake_ip_proxy_range_is_not_blocked_special_use` passed.
Browser spec was updated to lock the diagnostic class and was not re-run.
The capability probe still expects synthetic `{ok, supports_tools,
supports_json}`; a real provider can still fail after DNS. No commit SHA.
