# S48 — Build automatic proposal review and transparency UI (2026-10-09)

Automatic proposal review and transparency UI as wizard step 8: entry
flushes autosave and automatically creates/reuses a run (no Generate
click, no run per keystroke, gated on save/diagnosis/medication), ordered
seven-state progress with precise failed-question retry, lazy five-field
transparency from persisted review data, and final proposal with pinned
DDI coverage plus sign-blocked reasons. Backend needed no change;
existing `GET /generation-batches/{id}` + `GET /question-runs/{id}/review`
supply ordered states, baselines join, proposal/DDI, workflow, freshness,
and `safe_*` no-note-leakage. No clinical validation or live-provider
proof is claimed. Implementation + e2e are uncommitted.

## What works

- Entering step 8 flushes autosave, then auto starts/reuses at most one
  run per mount with `If-Match` + fresh `Idempotency-Key`; dirty/saving/
  failed/conflict saves, unacknowledged below-threshold diagnosis, and
  pending medication reconciliation all block with `Check again` and no
  POST; no Generate affordance; no run per keystroke.
- Reloads resume from `localStorage xi.proposal.<id>` via GET without a
  new POST; retries re-POST the stored exact packages; 404 recorded run
  clears storage to honest unavailable.
- Seven ordered states render with text + glyph; partial sections stay
  readable but incomplete; failed questions keep precise per-question
  retry; active polling (~2s, 15s hidden, immediate on visible, stop at
  terminal).
- Lazy transparency reads persisted `GET .../review` only (never
  recomputed from current chart): five fields + prompt/template versions,
  hashes, provenance; CPT percentages and computed posteriors labeled
  distinctly; failed originals expose no adjustable baseline.
- Final proposal shows position-ordered sections, skipped reasons, pinned
  DDI report with coverage warnings; stale/failed/clarification/incomplete
  visibly block signing with the exact reason while draft editing and
  retry stay available; secondary plan is a placeholder (S50).
- Page notes (`page="proposal"`) never enter batch/review payloads or the
  proposal DOM (sentinel assertions in routes + DOM).

## Follow-up 2026-10-22 — Step 7 cannot start a new proposal

- Confirmed source-level cause of the reported unavailable message:
  `ProposalReviewPanel.runStart` reads packages only from encounter-local
  `localStorage` (`xi.proposal.<encounterId>`). Without stored packages it
  returns before `startGeneration`, so no generation POST or provider call
  occurs. Completing the earlier wizard steps does not populate this key.
  Both application calls to `writeStoredProposal` happen only after a
  successful generation start/retry; there is no first-run package source.
  The existing fresh-entry browser test explicitly expects this unavailable
  state and zero generation POSTs; other proposal scenarios seed storage.
- The backend start contract still requires an inline `package` or `packages`;
  it does not resolve an encounter's workflow to released question packages.
  The message's S39 reference describes deferred integration, not a background
  task that waiting or reloading will complete. This is an application/content
  integration gap, not evidence of unfinished patient answers or a provider
  failure.
- Question-package approval is already recorded in S39.b. Historical bundles
  still pin predecessor drafts and await their own review. Runtime history
  integration also remains missing: a read-only call to the public
  `build_question_projection(manifest, {}, 1)` for each of the 11 approved
  `s39-reviewed-v1` manifests returned `422 unknown_source_path`. Path
  validation precedes patient-value resolution, so supplying more answers
  cannot repair this rejection. No deployment/database/browser storage was
  inspected; no active-pointer claim is made.
- Handoff: implement typed history/projection integration, prepare bundles
  pinning approved package revisions for their separate review/activation,
  and connect first-run generation to server-resolved pinned packages.
  Verify a new registration with no seeded browser storage, plus reload and
  another-browser recovery. Publishing DDInter resolves a separate dependency;
  it does not supply reasoning packages. No runtime/content approval changed.
- Verification: traced frontend storage reads/writes, backend start validation,
  the existing fresh-entry e2e assertion, and checked-in approval/bundle
  artifacts; reproduced all 11 projection failures without database/provider
  access. No browser suite rerun for this diagnosis-only follow-up.
